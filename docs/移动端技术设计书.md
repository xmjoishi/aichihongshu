# 爱吃红薯移动端技术设计书

## 1. 文档说明

- 文档目标：明确爱吃红薯移动端的产品范围、技术选型、核心架构和实施路径。
- 适用阶段：移动端 MVP 方案评审与落地前设计。
- 当前结论：移动端采用纯本地架构，AI 能力由用户自配 API Key，首版不依赖自建后端。

## 2. 范围边界

### 2.1 本次包含

- 相册浏览：显示系统权限允许访问的照片；应用标签与 AI 分析作为照片元数据。
- 笔记草稿：创建、查看、编辑、关联图片。
- AI 对话创作：基于人设、图片分析结果生成标题和正文。
- 发布辅助：复制文案、导出关联图片到独立相册、跳转小红书。
- 人设与设置：账号人设、本地 API Key 配置。
- 本地数据统计：围绕已使用照片记录、草稿、发布准备情况做轻量看板。

### 2.2 明确不做

- 不做桌面端 Playwright 自动发布能力迁移。
- 不做首版云端数据库和账号体系。
- 不做移动端与桌面端数据实时同步。
- 不做多人协作和跨设备共享。
- 不做视频笔记发布链路，首版仅支持图文内容。

## 3. 设计目标

- 围绕“小红书家居/软装/装修内容创作助手”主题，做一套更适合手机场景的工作流。
- 让用户可以直接在手机完成拍图、选图、出稿、复制发布素材的完整路径。
- 保留 AI 创作能力，但不引入服务端成本，降低产品早期试错门槛。
- 为后续付费版本预留扩展空间，但首版只解决单用户高频使用问题。

## 4. 产品定位与用户场景

### 4.1 产品定位

爱吃红薯移动端不是桌面端的简单镜像，而是围绕“手机随手拍、随手记、随手发”的创作工具重构。

### 4.2 目标用户

- 当前阶段：自己用的单用户工具。
- 后续阶段：可扩展为面向内容创作者的轻量付费产品。

### 4.3 核心使用场景

- 拍到一个家居角落、单品、布置灵感后，在系统相册中浏览；实际用于创作或笔记时再沉淀应用侧照片元数据。
- 在通勤、外出、逛店等碎片时间打开手机继续改草稿。
- 基于图片和既有人设，让 AI 协助出标题、正文、标签。
- 发布前一键复制文案，并将配图整理进独立相册，减少去小红书发布时的切换成本。

## 5. 总体方案结论

## 5.1 架构结论

- 客户端采用 `React Native + Expo`。
- 数据存储采用本地 `SQLite`。
- 系统相册负责原图，App SQLite 只存系统照片引用和自己的标签、分析及使用元数据；用户显式导出时才写入系统相册。
- AI 能力直接由客户端调用外部 API。
- API Key 由用户在客户端本地配置，敏感信息使用安全存储，不进入普通数据库。

## 5.2 为什么首版不做后端

- 图库、草稿、人设、发布辅助都属于强本地场景，天然适合离线保存。
- 当前产品仍在高频试错阶段，后端会显著增加部署、运维和多端同步复杂度。
- 用户接受自己配置 API Key 的模式后，AI 能力无需中转服务也可跑通。
- 真正必须依赖后端的能力主要是多人、多端同步、账号体系、服务端任务编排，这些都不在首版范围内。

## 6. 技术选型

| 层级 | 选型 | 说明 |
|---|---|---|
| 移动框架 | React Native + Expo | 开发效率高，生态成熟，适合快速验证产品 |
| 路由 | Expo Router | 文件路由，方便组织 Tab + Stack 结构 |
| 本地数据库 | expo-sqlite | 轻量稳定，符合单机数据存储需求 |
| ORM | Drizzle ORM | 便于 schema 管理和 migration 演进 |
| 状态管理 | Zustand | 简单直接，适合中小型应用 |
| 样式方案 | NativeWind + 自定义组件 | 保持与 Web 端较接近的样式表达方式 |
| 图片访问 | expo-image-picker | 支持拍照和相册选择 |
| 文件系统 | expo-file-system | 用于读取图片与临时转码，不长期保存系统照片副本 |
| 相册管理 | expo-media-library | 用于导出到系统相册和建立独立相册 |
| 剪贴板 | expo-clipboard | 用于复制标题、正文、完整发布文案 |
| 安全存储 | expo-secure-store | 存储 API Key 等敏感配置 |

```text
┌──────────────────────────────────────┐

│                                      │
│  Screens / Components                │
│          ↓                           │
│     Zustand Store                    │
│          ↓                           │
│      Service Layer                   │
│   ├─ db service                      │
│   ├─ ai service                      │
│   ├─ media service                   │
│   └─ publish helper service          │
│          ↓                           │

│          ↓                           │
```

### 7.1 模块职责

- UI 层：负责展示相册、草稿、对话、设置等交互界面。
- Store 层：维护当前选中的图片、草稿、会话状态、设置状态。
- Service 层：封装数据库读写、AI 调用、系统照片读取/导出、剪贴板和相册操作。
- 存储层：分别处理普通业务元数据、系统照片引用、临时转码资源和敏感配置。

## 8. 信息架构与页面设计

建议采用 4 个主 Tab。

### 8.1 相册 Tab

- 功能：按系统照片权限查看图片网格、查看应用标签与分析结果、多选 AI 分析或关联笔记。
- 重点：浏览与选图立即响应；仅照片实际被使用或保存为笔记关联时创建应用元数据记录。

页面建议：

- 相册首页：系统照片三列网格；照片标记分为已入库、已分析/未分析、已使用等可重叠状态。
- 图片详情：大图、标题、标签、AI 分析、关联草稿入口；系统原图不可访问时保留元数据并展示提示。

### 8.2 创作 Tab

- 功能：选择图片、进入 AI 对话、生成内容、保存草稿。
- 重点：图片和对话同屏或上下联动，降低上下文切换。

页面建议：

- 创作首页：最近草稿、推荐继续写的条目。
- AI 对话页：上方图片卡片，下方聊天输入区。
- 草稿编辑页：标题、正文、标签；图片条为小红书式交互——长按拖动排序、首图即封面、右上角 × 删除（二次确认）、末尾「加图」、点首图进笔记预览页（图/标题/正文、预览封面、发笔记）。

### 8.3 发布 Tab

- 功能：查看待发布草稿、复制文案、系统分享面板直发图片到小红书、备用导出图片到相册、跳转小红书。
- 重点：把“发布前准备动作”一次性做完；分享为主链路，导出相册为备用。

页面建议：

- 待发布列表页：按更新时间排序。
- 发布详情页：复制标题、复制正文、复制全文、「分享到小红书」（系统分享面板带图+文案）、备用导出图片到相册、打开小红书。

### 8.4 我的 Tab

- 功能：配置人设、查看数据统计、设置 AI Key。
- 重点：管理系统提示词底座和个人使用习惯。

页面建议：

- 人设页：昵称、赛道、语气、禁忌词。
- 设置页：API Key、默认模型、图片分析开关等。

## 9. 核心数据模型

### 9.1 items 照片元数据表

```sql
CREATE TABLE items (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  image_path TEXT NOT NULL,
  source_asset_id TEXT,
  tags TEXT DEFAULT '[]',
  analysis TEXT,
  used_at TEXT,
  usage_sources TEXT DEFAULT '[]',
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

字段说明：

- `image_path`：系统照片 URI；优先通过 `source_asset_id` 匹配系统照片。没有稳定 asset ID 时回退保存选择器 URI，该 URI 可能随系统或缓存清理失效。
- `source_asset_id`：按平台命名空间保存的系统照片 ID，用于把应用标记重新匹配到系统相册中的照片。
- `tags`：JSON 数组。
- `analysis`：图片分析文本，后续作为 AI 创作上下文的一部分。
- `used_at` / `usage_sources`：首次实际使用时间和使用入口集合；入库、分析、使用是可重叠维度。
- `items` 只记录被实际使用或明确关联到笔记的照片；浏览系统相册和暂存选图 URI 不创建行。

### 9.2 notes 草稿表

```sql
CREATE TABLE notes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT,
  body TEXT,
  tags TEXT DEFAULT '[]',
  item_ids TEXT DEFAULT '[]',
  status TEXT DEFAULT 'draft',
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

字段说明：

- `item_ids`：关联的图库图片 ID 列表。
- `status`：建议支持 `draft`、`ready` 两种状态。

### 9.3 profile 人设表

```sql
CREATE TABLE profile (
  id INTEGER PRIMARY KEY DEFAULT 1,
  display_name TEXT,
  niche TEXT DEFAULT '家居软装/出租屋改造',
  persona_name TEXT,
  persona_bio TEXT,
  persona_tone TEXT,
  taboos TEXT DEFAULT '[]',
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

### 9.4 settings 配置表

```sql
CREATE TABLE settings (
  key TEXT PRIMARY KEY,
  value TEXT
);
```

说明：

- 普通配置写入 `settings`。
- 敏感配置如 `MINIMAX_API_KEY` 存 `expo-secure-store`，不写入 SQLite。

## 10. 核心流程设计

### 10.1 图片导入流程

```text
按 iOS / Android 权限读取系统相册照片
→ 选图后先保存到页面临时状态并立即预览
→ 浏览、取消或从未使用的选择不写入 items
→ 图片实际用于 AI 创作、AI 分析、笔记关联或 PC Harness 后，按系统 asset ID 创建/复用 items 元数据记录
→ AI 分析完成后更新 analysis；每类实际使用入口追加到 usage_sources
```

设计要点：

- 系统相册持有原图，应用不复制图片字节；SQLite 仅保存 URI、系统 asset ID、标签、分析和使用元数据。
- 页面预览先于入库，避免选图等待数据库写入；AI 请求前再从系统 URI 读取、必要时转码。
- 相册首屏分页读取 36 张；照片格进入可视区域后才尝试读取 iCloud 原图；本机已有照片先尝试本地 URI，滚动不扫描完整图库。
- 相册页重新获得焦点、系统照片变化或权限选择器关闭后立即刷新第一页，避免新授权照片要等下一次操作才出现。
- 入库不自动等同于已分析；未分析统计仅针对已经入库的照片。
- Android Photo Picker 或没有稳定 asset ID 的临时 URI 可能无法长期访问；优先保存平台 asset ID，访问失败时保留元数据并显示原图不可访问提示。

### 10.2 AI 创作流程

```text
选择图片
→ 读取 profile + 图片 analysis
→ 组装 system prompt
→ 用户输入创作意图
→ 调用 AI 文本生成接口
→ 输出标题、正文建议
→ 用户选择保存草稿
```

设计要点：

- 人设信息必须参与 prompt 组装。
- 支持把多张图片的分析结果拼接后喂给模型。
- 对话结果应支持“一键写入标题/正文”。

### 10.3 发布辅助流程

```text
打开待发布草稿
→ 点「分享到小红书」：关联图片 + 文案进系统分享面板
→ 面板选择小红书，图片与文案带入编辑器
→（兜底）文案同时自动写入剪贴板，可手动粘贴
→（备用）导出关联图片到系统相册指定相册后跳转小红书
```

设计要点：

- 分享链路与系统相册「分享」一致，仍是人工交接，不自动发布。
- 相册名可优先使用笔记标题，失败时降级为固定相册名。
- 全文复制内容建议统一格式，减少用户手动整理。

## 11. AI 设计

### 11.1 用户自配 API Key 方案

- 用户在设置页输入 API Key。
- App 使用 `expo-secure-store` 保存 Key。
- 每次请求 AI 时从安全存储读取 Key。
- 设置页展示时默认脱敏。

### 11.2 为什么允许客户端直连 AI

- 这是单用户工具，用户自行承担自己的 AI 用量成本。
- 不需要平台统一结算和用量管理时，服务端代理价值不大。
- React Native 是原生应用环境，不存在浏览器 CORS 问题。

### 11.3 风险控制

- 开发模式下要避免在日志中打印完整请求头。
- 网络失败、Key 失效、额度不足都要给出明确提示。
- 后续若转向付费产品，再切换成服务端代理模式。

## 12. 文件与图片管理设计

### 12.1 系统照片引用与应用元数据

- 相册页只展示系统权限允许访问的照片；iOS limited 权限下允许用户从系统选择器调整授权范围。
- 系统相册持有原图；SQLite 只存照片引用和 App 自己的标签、分析、笔记关联、使用状态，不保存原图字节。
- 照片在系统相册中删除或权限被撤回后，保留应用元数据；图片组件显示「原图不可访问」。重新授权后按系统 asset ID 重新匹配。
- AI 识别所需的解码/HEIC 转 JPEG 使用临时处理结果，不把转码文件作为图库副本长期保存。

### 12.2 独立相册能力

- 选择草稿后，将其关联图片批量保存到系统相册。
- 优先为当前草稿创建独立相册，方便去小红书选图时快速定位。

### 12.3 删除策略

- 删除照片标记时仅删除 App 内部元数据记录，不删除系统相册照片。
- 已导出到系统相册的图片不做回收，以免误删用户外部数据。

## 14. 与现有项目的关系

### 14.1 可复用部分

- 现有业务领域模型：图库、草稿、人设这三块概念可直接复用。
- 现有 AI prompt 组织思路：图片分析 + 人设 + 创作诉求的组合方式可沿用。
- 现有字段命名：尽量和桌面端保持接近，降低理解成本。

### 14.2 不建议直接复用部分

- `client/` 当前 Tauri Web UI 不适合直接搬到 React Native。
- FastAPI 路由层和 MCP Server 对移动端首版没有必要。
- Playwright 自动发布链路不适合移动端场景。

## 16. 风险点与测试点

### 16.1 风险点

- iOS 和 Android 的相册权限行为不同，需要分别验证。
- 小红书 App Scheme 跳转能力在不同机型上可能有差异。
- 用户直接配置 API Key，会带来输错、额度不足、模型变更等问题。
- 大图导入和 base64 编码可能导致内存压力，需要限制单次分析图片尺寸。

### 16.2 测试点

- 首次打开时的权限申请路径是否顺畅。
- 系统相册选图后是否立即预览，取消或仅浏览是否不创建照片元数据记录。
- 照片实际用于 AI、笔记关联或 PC Harness 后，是否创建/复用正确的系统照片引用记录。
- API Key 未配置、配置错误、网络失败时的错误提示是否清晰。
- 单图和多图创作时，AI 上下文是否正确拼接。
- 复制标题、正文、全文后内容格式是否正确。
- 导出到系统相册后，图片是否能被小红书正常选取。

## 17. 待确认事项

- 是否需要首版支持 Android 和 iOS 同时上线，还是先只做 iOS。
- AI 模型是否只支持 MiniMax，还是预留 OpenAI 兼容接口。
- 是否需要在移动端保留“参考账号”能力，还是先聚焦相册和创作。
- 后续若要做多端同步，是否以桌面端为主库，还是直接引入云端统一存储。
