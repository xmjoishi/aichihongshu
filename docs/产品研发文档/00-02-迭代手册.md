# 产品迭代手册

本手册规定本项目“产品负责人 + AI”协作迭代的入口、变更记录、实施、验收和归档方式。产品负责人决定目标、关键取舍和产品验收；AI 负责调查、实现、适当验证和文档闭环。用户最新指令优先；已确认事项不重复询问。

## 任务入口

| 入口 | 处理方式 | 是否建立 CHG |
| --- | --- | --- |
| 想法记录 | 写入 [TODO 想法索引](./TODO/00-01-想法索引.md)，明确尚未承诺实施 | 否 |
| 正式需求 | 先检查现状并澄清会影响实现或验收的事项，再形成方案和验收条件供产品负责人确认 | 确认进入实施后建立；需要持续澄清和追踪时可先建“待确认”CHG |
| 继续变更 | 以主题、对象和验收目标判断是否属于已有工作；属于同一目标的修复、补充和复验沿用原 CHG | 不重复建号 |
| 直接作业 | 只读调查、文档整理、测试、构建和环境检查直接完成并报告结果 | 否 |

每次询问只针对会改变产品行为、数据语义、范围、风险或验收结果的未决问题。已有明确结论从确认卡和实施记录读取，不重新确认。实现中若出现超出确认范围的重大变化，先完成不依赖该决定的工作，再就新增决定对齐。

## 一个目标，一个变更包

正式变更在 `docs/产品研发文档/ING/CHG-YYYYMMDD-NNN-简短名称/` 建立唯一变更包。建立前查看 ING 索引，沿用下一个可用编号；跨会话、换执行者或修复验收问题都继续沿用原 CHG。

普通变更维护两份正文：

1. `00-01-变更确认卡.md`：目标、当前与期望行为、范围、非目标、已确认决定、待决问题、按编号编写的验收条件，以及受影响的文档落点。
2. `00-02-实施与验证记录.md`：顶部恢复检查点、实现结果、修改范围、验证命令及结果、产品验收证据、文档同步状态、遗留事项和下一步。

只有架构迁移、数据模型、安全边界或跨模块依赖确实需要时，才增加技术设计或测试设计。按需增加，不为流程本身机械增加文件。确认卡定义目标和验收；实施记录只写最终实际发生的事，方案变化要同步修正确认卡和设计，不保留互相矛盾的多份“现行”答案。

## 状态流转

| 状态 | 进入条件与要求 |
| --- | --- |
| 待确认 | 目标或方案仍在澄清；记录已知事实、关键问题和不依赖答案可先做的工作。 |
| 已确认待实施 | 产品负责人已确认目标、范围和关键取舍；确认卡含可观察的验收条件。 |
| 实施中 | 正在按确认范围修改代码或文档；实施记录和 ING 索引反映当前阶段。 |
| 待验收 | 必要的自动检查已完成；向用户提供逐项操作步骤和预期结果。构建通过不等于产品验收通过。 |
| 待复验 | 用户验收发现问题；在原 CHG 记录问题、修复、复验步骤和结果，修复后返回待验收。 |
| 待归档 | 用户验收通过，正在完成下方文档同步和一致性检查；同步未完成时不得标为已完成。 |
| 已完成 | 适用的文档落点已更新或注明无需更新原因，索引和完成变更记录已同步，一致性检查通过。 |
| 暂停 | 用户明确要求暂停；记录暂停时的状态、未完事项和恢复入口。普通阻塞记录原因与下一步，不用“暂停”掩盖。 |

状态主路径为：`待确认 → 已确认待实施 → 实施中 → 待验收 ⇄ 待复验 → 待归档 → 已完成`。暂停可发生在任何未完成阶段；恢复时从记录的原阶段继续。现有 CHG 按当前项目惯例保留状态，更新时逐步迁移，不要求为采用本手册批量改写历史文件。

## 实施与验证

按变更影响选择验证，不默认每次运行所有测试。常见顺序为目标代码检查/类型检查、受影响的自动化测试、必要的集成验证和构建；命令应与实际范围相符。若用户明确限制自动化测试、真实模型调用或外部操作，按限制执行并在记录中写明未运行项及其影响。

原生窗口行为、启动与恢复、文件选择、账号隔离、迁移、浏览器链路和平台发布等场景，需用对应真实路径或专门隔离环境验收；普通构建不能替代这些检查。发布、删除、正式数据迁移及对外提交遵守项目授权和安全边界，未授权时只完成准备和可审阅结果。

实施记录顶部的恢复检查点至少包括：更新时间和当前阶段、完成项、已确认与待决事项、修改文件与代码基线、无关工作区脏状态、验证结果、阻塞及下一步。实施阶段切换、中断或交接前更新检查点；先保留无关未提交改动，不自动提交、推送或清理用户资料。仓库特有工程边界以根目录 `AGENTS.md` 为准。

## 产品验收

每个验收条件使用稳定 AC 编号，并写清：

- 操作步骤和所需账号/数据/环境；
- 用户能观察到的预期结果；
- 验收责任人；
- 实际结果、证据、日期和通过/失败状态。

默认由用户在真实交付环境验收。只有用户明确委托 AI 代验时，AI 才在隔离资料和授权范围内操作真实桌面或浏览器路径。问题回到原 CHG，状态转为待复验；修复后重新执行受影响 AC。自动测试通过、截图看似正确或实现者自测均不能替代用户产品验收，除非用户已明确委托对应验收。

## 验收通过后的文档闭环

进入待归档后，对以下各项逐项写入实施记录的同步表。每项必须有更新位置和摘要；确实不受影响时写明原因；未完成项要有责任人或后续步骤，不能提前关闭 CHG。

| 同步项 | 检查与更新要求 |
| --- | --- |
| 产品与设计 | 根据最终实现和验收修正产品规划、交互/技术设计；说明相对确认方案的差异。 |
| 当前事实 | 将已实现且已验收的产品行为、技术实现、数据规则、边界和限制写入对应 RESULT 产品事实/技术事实；未实现或未验收内容不得写为现行事实。 |
| 完成变更记录 | 在 `docs/产品研发文档/RESULT/00-01-变更记录.md` 记录原因、结果、事实落点、验收日期和发布状态，并从 ING 索引可追踪到对应 CHG。 |
| 发布说明 | 用户可感知的新增、优化、修复、兼容变化和已知限制同步到 `docs/CHANGELOG.md`。验收通过但尚未发布的条目标为未发布/待发布，不暗示已交付到正式版本；正式发布另走发布门禁。 |
| 操作手册与引导 | 若用户操作、入口、步骤或限制有变化，更新唯一操作正文 `docs/操作手册.md`，并检查用户手册总览入口。若该功能另有应用内教程/帮助内容源，同步更新该源；仓库当前没有独立教程内容文件时，记录不适用，不虚构新事实。 |

完成前核对代码、最终确认卡/技术设计、产品事实、技术事实、发布说明、操作手册、验收证据彼此一致。更新 ING 索引状态和下一步；同步完整后写入完成变更记录，将 CHG 标为已完成。变更包正文按现有目录惯例保留并由 RESULT 记录链接，不因“归档”随意移动或复制出第二份正文。隔离验收临时对象可在确认不再需要后清理；用户资料、正式数据库、凭据和未授权外部记录不得顺手清除。

## 正式发布门禁

`已完成`表示代码变更和产品/文档闭环完成，不自动表示已发布。正式发布需单独记录版本号、完整发布门禁结果、最终产物验证、冻结后的发布说明及发布状态。**实现完成、用户验收通过、变更归档完成、正式发布是四个独立事实。**
