# 文档与 AI 协作规则

## 事实分层

- TODO：想法索引，一行即可，不承诺实现。
- ING：正在澄清、实施或验收的变更，一个任务一个 CHG；换模型或会话不重新编号。
- RESULT：已核实的当前产品/技术事实；新能力须验证并经用户验收后写入，不复制讨论历史。现状整理应注明证据与限制。
- 发布说明：用户可感知的版本变化，验收后可写“未发布”，不得暗示已经发布。
- 用户手册：当前正确操作方式。

## 最小变更包

普通变更使用确认卡、实施与验证记录；架构迁移、数据、安全或跨模块改动增加技术设计。确认卡记录目标、现状、范围、非目标、已确认决定、待决事项、编号验收条件和文档影响。技术设计记录代码入口、责任边界、迁移及兼容策略、实施顺序和停止条件。

状态使用：待对齐、已确认待实施、实施中、待验证、待用户验收、暂停、完成。索引链接任务包，记录负责人、代码基线和下一步；状态变化同时更新检查点。

## 授权与分工

产品方确认范围和产品验收；计划协作者维护方案；执行者负责实现、自动验证及记录。具体模型由用户指定，不写死。用户最新指令优先，已经授权的范围不重复询问。只暂停会改变产品行为、数据语义、权限或验收结果且尚未确定的步骤，独立工作继续推进。

## 验证与交付

按改动运行必要的自动测试、Rust/前端检查与构建。每项产品验收使用 AC 编号，包含步骤、可观察预期、实际结果及责任人。默认用户进行产品操作验收；用户明确委托时由 AI 执行真实桌面/浏览器路径。使用隔离测试资料，不操作正式账号发布，除非已有明确授权。浏览器检查不替代 Tauri 原生窗口、文件选择和重启恢复验收。

区分实现完成、验收完成、发布完成。未验证、失败或阻塞不得标成通过。

## 恢复检查点

实施记录顶部固定维护：更新时间、当前阶段、完成项、已确认与待决事项、修改文件及代码基线、无关脏文件、验证结果、阻塞和下一步。阶段完成、中断或交接前更新；新会话先读检查点，再核对 git status 和最新用户指令。

## 收尾

每个 CHG 判断产品事实、技术事实、发布说明、用户手册、完成记录五个落点；仅更新受影响内容，其余写明无需更新原因。完成后更新 ING 索引状态与 RESULT 变更记录；保持唯一正文和可追踪链接。文档整理本身不需要另起 CHG，不提前宣称功能实现。
