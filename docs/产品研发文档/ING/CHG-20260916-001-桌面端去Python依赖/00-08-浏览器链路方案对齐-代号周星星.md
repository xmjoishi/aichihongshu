两条不可丢弃的工程约束（换任何方案都保留）：

1. macOS 上 Chromium cookie 经 Keychain 加密，必须经 Playwright/CDP API 打开浏览器，不能直接 exec Chromium 二进制（否则 `launch_persistent_context` 读不到登录态）。
2. `xsec_token` 只有从搜索结果点击进入才会出现，采集必须走页面交互而非直拼 URL——这本身就是风控要求，不是可绕过的实现细节。

## 3. 三条候选路线对照（D4 具体化）

| 维度 | A 独立受控会话 | B 扩展/Native Messaging 接管用户 Chrome | C 混合 |
| --- | --- | --- | --- |
| 形态 | 自带 Chromium（Node sidecar Playwright 或 Rust `chromiumoxide` 直连 CDP） | Chrome 扩展 + native host，列出/认领用户真实标签页（Codex Chrome Control 模式） | 剪藏与发布走 B，批量采集走 A 限频或降级为人工导入 |
| 登录态 | 独立 profile，需扫码一次 | 直接复用用户真实登录态 | 两者皆有 |
| 剪藏（N12） | 可做，需用户在受控浏览器里浏览 | 天然契合（用户日常浏览中剪藏），确认卡既定倾向 | B |
| 采集 | 全覆盖，继承 MediaCrawler 能力 | 可做但受限于用户标签页模式，批量场景别扭 | A 低频 |
| 发布 | 全自动可做，但全自动提交风险最高 | 填充到用户真实标签页、人工点击提交，与 N13「手动确认已发布」语义完全对齐 | B |
| 指纹真实度 | 中（默认有可检测特征，需反检测发行版补齐） | 高（真实 Chrome、真实日常环境） | 按通道 |
| 实现复杂度 | 低（Node sidecar 几乎平移现有脚本） | 高（native host、扩展安装与授权、权限模型） | 中 |
| 平台限制 | 仅 Chromium 系可控；Firefox 需另选型（如 camoufox 类） | 仅限 Chrome | 按通道 |

要点：

- 确认卡 D4 已倾向「扩展/Native Messaging 优先」；对照表明该倾向与 N12（剪藏）、N13（发布人工确认）语义高度吻合。
- 但扩展路线对「批量采集」不是好形态；采集要么走 A 低频，要么接受降级。采集规模本身待用户定风险水位。
- 去 Python ≠ 去浏览器自动化：Playwright 是 Node 一等公民，A 路线以 Node sidecar 落位与 Tauri 兼容；真正要重新落位的是旧能力对 MC_PYTHON（MediaCrawler venv）的寄生关系。

## 4. 风险分层与红线

封号的主因是行为模式而非所用库。Playwright 默认确有可检测特征（`navigator.webdriver`、headless 指纹、CDP `Runtime.enable` 泄漏），可由反检测发行版缓解；但决定处罚的是下表右列。

| 操作 | 风险 | 设计含义 |
| --- | --- | --- |
| 扫码登录/登录态保活 | 低 | 正常流程保留 |
| 剪藏/用户触发的单页读取 | 低 | N12 按此水位实施 |
| 小批量采集（几十条/次 + 随机间隔） | 中 | 需每日配额；量大会先被限流（返回空数据） |
| 大批量持续采集 | 高 | 默认不提供；如需要，单独对齐 |
| 自动发布（全自动写入） | 最高 | 默认改为「自动填充 + 人工点击提交」 |

减险清单（前两条现状已满足）：有头 + persistent context；单账号独立 `browser_profiles/<account>`（N00 已建目录边界）；反检测发行版（patchright/rebrowser 类）作为可选依赖策略待 D4-c 决策；频控内建（分钟级随机延迟、每日配额、采集与发布账号分离）；`connect_over_cdp` 接管用户日常 Chrome 作为更彻底的替代形态。

红线：

1. MediaCrawler 子模块不改；仅学习/研究用途边界沿用（不商业化）。
2. 不自动提交/不重复提交：发布状态沿用 N13 的「结果不明不重发」模型。
3. 不把登录态、Cookie、浏览器 profile 写入 QA、日志或仓库。
4. 权限最小化：扩展申请的权限范围（站点、标签页读取）先在 D4 决策中列明再实施。

## 6. D4 定向后执行计划：N12 扩展剪藏最小原型

既有 N12 契约（`browserCapture.ts` 校验/队列 + `inspirations` 表 + `save_local_inspiration`）已就位，本原型只补「真实浏览器链路」这一段：扩展仍是纯消息传输，不碰数据库、Cookie、浏览器 profile。

目标链路：

```
Chrome 扩展（MV3；点击按钮时经 activeTab 注入抓取当前页 title/URL/划词/正文）
  → chrome.runtime.sendNativeMessage（stdio 长度前缀 JSON）
  → 原生宿主（Node 脚本，由 Chrome 拉起）
  → 本机回传通道（二选一，原型实测）
       候选1：127.0.0.1 + 一次性 token（Tauri 启动生成，宿主经 owner-only 文件读取）
       候选2：owner-only Unix domain socket（Codex Chrome Control 同款形态）
  → Tauri Rust 接收：镜像再校验 + 以当前激活账号盖章 targetAccountId
  → Tauri 事件 → WebView 既有 acceptCapture（AICHIHONGSHU_BROWSER_CAPTURE 通道）
  → 待确认队列（幂等 requestId/dedupeKey）
  → 用户确认 → save_local_inspiration 入库
```

扩展权限清单（最小、可见、可撤销，MV3）：

- `"permissions": ["nativeMessaging", "scripting", "activeTab"]`
- 不申请：`tabs`、`cookies`、`history`、`browsingData`、`<all_urls>`/host 权限、常驻 content script
- 仅在用户点击扩展按钮时对当前标签页 `executeScript`

安装路径（均为用户显式操作，会话不自动写入）：

- 扩展：Chrome 开发者模式「加载已解压」指向仓库目录；manifest 固定 `key` 以稳定扩展 ID
- 原生宿主 manifest：`~/Library/Application Support/Google/Chrome/NativeMessagingHosts/com.aichihongshu.host.json`（用户级、无需 root；`allowed_origins` 绑定扩展 ID），由 install 脚本生成、用户执行

再校验（不盲信扩展输入）：

- Rust 侧镜像 `browserCapture.ts` 契约：128KB 上限、http(s) URL、字段上限、非空标题
- `targetAccountId` 由 Rust 以当前激活账号写入，不采纳扩展提供的值
- WebView 沿用既有幂等队列与失败重试

QA 边界：验收在 `.qa/desktop-workspace`（QA-A/QA-B）进行，不写正式 `data/app.db`；不接真实登录态；测试页用本地 fixture 或公开页。采集/发布链路不在本原型范围。

验收：补齐 N12-AC1（真实扩展→队列→确认入库、账号归属正确）与 N12-AC2（记录浏览器/版本、权限清单、失败反馈）的真实链路证据。

授权边界：仓库内代码（扩展源、宿主脚本、Rust 接收与再校验、WebView 事件接线、契约测试）属 CHG 实施范围；写入 `~/Library` 的宿主 manifest 安装、Chrome 加载扩展、真实页面剪藏验收属用户显式操作/外部授权；每步开始与结束更新 00-03 检查点。

后续（本原型之外）：采集侧 A 路线 Node sidecar 落位草案、D4-c 风控证据观察窗口、N13 发布填充链路，另行按任务卡推进。
